# PRS Coverage Review

This is a source-level coverage review against `SOFT2027_PRS_v1.0`. A listed screen or code path is evidence of implementation, not proof that every workflow has passed acceptance testing with the business.

## Areas represented in the application

| PRS area | Current application coverage |
|---|---|
| Sales and purchases | Entry screens, line items, payment/balance fields, saved transaction pricing, and posting workflows are present. |
| Returns | Sales and purchase return screens load original transaction lines and enforce return quantity limits. |
| Inventory | Current stock, movement history, stock adjustments, and low-stock count are present. |
| Master data | Product, customer, supplier, category, brand, and unit management screens are present. |
| Ledgers and finance | Customer/supplier ledgers, receipts, payments, expenses, and cash/bank screens are present. |
| Administration | Administrator management and audit-history screens are present. |
| Security and offline operation | Hashed administrator credentials, session-based access, local SQLite storage, and self-contained Windows publishing are present in the source. |
| Data safety | Backup and restore screens/services are present. |
| Numeric quantity entry | Numeric validation and Up/Down keyboard increments are applied to sales, purchase, return, and stock adjustment quantity fields. |

## Requirements that remain incomplete or need business confirmation

- **Invoice and purchase document print/preview:** Sales and purchase screens expose saved-transaction history, lookup by invoice/bill number, preview, and a Windows print dialog. Individual documents use transaction-saved amounts and line snapshots. Sales also offers a compact A4 portrait sheet containing up to four distinct recent posted invoices, following the supplied four-cash-memos-per-page example. Sale/purchase line product code and name snapshots are persisted for future transactions, with an idempotent migration backfilling existing rows from the product catalog when the app is next opened. The supplied contact line (Latifabad No. 11; 0336-1841496) and signature labels are included. The samples do not show terms or a purchase bill; have Ali Traders approve the final wording/layout, paper, orientation and printer output before release sign-off. WPF Release compilation and automated saved-value/reprint safety checks pass; a physical printer and Windows dialog run were not available for verification here.
- **Reporting breadth:** The Reports screen exposes the requested sales, purchase, inventory, customer, supplier, financial, and pricing report catalog with shared date/party/product/category filters, empty states, and CSV export. Queries read persisted transactions, historical line-price/cost snapshots, returns, ledgers, cash/bank rows, and expenses. Product profitability uses saved sale-line costs less returned cost estimated at the original invoice's weighted historical cost; stock valuation uses current quantity multiplied by current default purchase price. Operational report repository tests and end-to-end sales/P&L/stock reconciliation tests pass for the known SQLite fixtures.
- **Dashboard breadth:** The Reports Dashboard now shows today's and selected-period sales/purchases, daily sales/purchase trends, receivables/payables, stock valuation, low-stock count, and chronologically sorted recent sales, purchases, receipts, payments, and stock adjustments. Metrics query persisted operational reports; opening reports reloads the dashboard. Activity rows navigate to the corresponding module. End-to-end checks reconcile the sales figures to P&L for the seeded dataset.
- **Pricing memory and calculations:** Sales and purchase entry restore previous pair-specific rates, percentages, discounts, date, quantity and document reference; explicit Default and New choices are retained and posted values enter price history atomically with the transaction. Product master rejects negative prices. `SellingPercentage` means markup over cost (not gross margin); `PurchasePercentage` is stored as a reference only and is not applied as a second discount. Selection, first-time-pair, edited-default, discount and historical reprint cases have automated coverage.
- **Bank workflow:** Bank transaction storage exists, but bank transfers and the exact bank workflow need business confirmation as noted by the PRS.
- **Sales, purchases, returns and ledgers (Work Package E):** Posting is atomic across the original document, saved line snapshots, inventory movement, party balance/ledger, pricing memory, cash/bank entries (when paid) and audit log. Service-level validation rejects sales that would create negative stock and inconsistent paid/remaining totals. Return posting checks cumulative returned quantity against original quantity within the same database transaction; repeated partial returns work and an over-return rolls back without mutation. Receipts and payments can be repeated in partial amounts, are routed to cash or bank by payment mode, and cannot exceed the party's current outstanding balance. Database uniqueness on document/reference numbers prevents an operator retry from posting the same reference twice. Returned goods are currently all added back to stock for sales returns or removed for purchase returns; saleable/damaged disposition is not separately modeled and needs a business rule if required.
- **Inventory integrity (Work Package F):** Purchases and sales adjust stock with movement rows; returns reverse quantities; manual adjustments require a reason and reject a negative resulting balance. Decimal/fractional quantities are retained. Automated scenarios reconcile repeated fractional returns and failed sale/return operations against stock balances and movement/document records. Opening stock and valuation still follow the application's existing stock ledger/current default purchase price rules; confirm the cost basis with the customer.
- **Cash, bank and financial integrity (Work Package G):** Sales/purchases paid at posting and standalone receipts/payments/expenses update the selected cash or bank ledger atomically. Automated scenarios cover repeated partial receipts/payments on cash and bank and compare running balances with party balances. Existing schema supports opening entries. Inter-account transfers remain unimplemented pending customer confirmation of workflow and transfer requirements.
- **Desktop UI/UX and window controls (Work Package H):** The WPF window uses Windows `WindowChrome` resize/caption behavior, standard minimize/maximize/restore state changes, a 980×560 minimum, and work-area bounds. Closing while a sales, purchase, or return draft contains line items now prompts before discarding. Shared mouse-wheel routing scrolls the nearest eligible table/panel and hands off to outer page scrolling at boundaries; the Reports Dashboard no longer nests a page scroller inside the workspace. Button hover/pressed states preserve each semantic color and readable text; disabled controls use a contrasting neutral treatment and controls have a keyboard-focus outline. The Release build and 129-test suite pass. A manual native-desktop interaction and visual layout pass was not possible in this environment because the computer-use connector exposes no Windows app/window controls; run the button-state, wheel, window-control, resize, dialog, and layout checklist on the target Windows desktop.
- **Administration, security and audit (Work Package I):** First-run setup is one-time, passwords are stored using salted PBKDF2-SHA256 hashes, invalid credentials are rejected, the last active administrator cannot be disabled, protected transaction posting requires an administrator session, and important administrator/login/transaction actions write audit rows. Automated repository checks cover hashing, first-run setup, login failures/success, deactivation, reset, and audit history. Credentials were not entered into the running UI during this review.
- **SQLite data safety (Work Package J):** Startup initializes the schema idempotently and applies the item snapshot upgrade. Multi-record business postings use transactions. Backup uses SQLite's online backup API. Restore now checks required SOFT2027 tables, SQLite integrity, and foreign-key consistency before replacing the live database; it first saves a safety copy. Automated tests cover snapshot consistency, successful restore, invalid/inconsistent backup rejection, and preservation of existing live data. The application defaults to `%LOCALAPPDATA%\SOFT2027\soft2027.db`; restore safety copies are placed in its `Backups` folder. A `SOFT2027_DATABASE_PATH` override supports isolated local testing.
- **Production acceptance:** Native Windows UI interaction and layout, damaged-return handling if needed, role restrictions through the UI, printer output, stock valuation cost basis, opening stock setup and business acceptance still need confirmation using a disposable test database and target Windows hardware. The complete current automated solution suite passes (129 tests); passing the suite does not replace business sign-off. Receipt/payment over-settlement is rejected; confirm whether customer or supplier advances should be supported as separate account entries.
- **Windows packaging (Work Package K):** A self-contained x64 portable-folder release candidate (`1.0.0-rc.2`) and ZIP are produced, with install/update/uninstall/data-location guidance and optional current-user shortcut scripts. Customer selected portable format; there is no MSI/installer. The executable starts against a disposable database on the development host. Clean Windows install/update/uninstall, shortcut execution, approved icon, signing, and target Windows compatibility still need manual acceptance. The build targets .NET 8; review framework lifecycle before production.
- **Testing and handover (Work Packages L–M):** The full automated solution suite passes (129/129). The package includes the user guide, release notes, installation/handover notes, schema, and final test report. Native UI, printer and clean-machine checks remain pending; see `FINAL_TEST_REPORT.md`. Production sign-off remains withheld pending customer approvals and manual acceptance.

## Verification boundary

The Release build and automated suite do not demonstrate recovery from interrupted writes, correct migration of a production database, physical printer compatibility, or customer acceptance. Verify an existing-database upgrade and the final documents on target Windows hardware before production use.
